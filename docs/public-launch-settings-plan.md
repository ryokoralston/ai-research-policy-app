# 一般公開に向けた設定機能・設計プラン

- **作成**: 2026-08-03
- **目的**: このアプリを社外の顧客に使ってもらう前提で、必要な設定機能と、その前提となる
  データ構造の変更を洗い出す。
- **状態**: 設計案。実装前の検討資料であり、着手済みの項目はない。

---

## 1. 結論(先に)

設定「画面」を増やす前に、**データの所有者の概念**を入れる必要がある。現状はシングル
テナント設計で、ログインした全ユーザーが同じリサーチ履歴・ドキュメント・レポートを共有
している。この状態で公開すると、設定機能の出来に関わらず顧客同士のデータが混ざる。

推奨する順序:

1. データのスコープ化(所有者の付与)
2. 使用量の計測とレート制限
3. Account / Privacy 系の設定
4. 課金(計測データが貯まってから)

---

## 2. 現状の構造的制約(コード調査の結果)

### 2.1 所有者を持つテーブルは監査ログだけ

`backend/models/` を確認したところ、`user_id` を持つのは `audit_log` のみ。

| テーブル | 所有者 | 公開時に起きること |
|---|---|---|
| `research_sessions` | なし | 全顧客が互いの調査内容を閲覧できる |
| `documents` / `document_chunks` | なし | アップロードした資料が全員に見える。RAG検索も全員分を横断する |
| `reports` / `report_sections` | なし | 同上 |
| `debates` / `debate_arguments` | なし | 同上 |
| `risk_analyses` | なし | 同上 |
| `reminders` | なし | 同上 |
| `custom_personas` | 管理者が全体管理 | 意図的な共有。組織単位なら妥当だが、顧客をまたぐと不可 |
| `audit_log` | **あり** | 現状で唯一正しくスコープされている |

### 2.2 設定テーブルは単一行

`database.py` の `get_or_init_model_settings()` は「the single ModelSettings row」として
`db.get(ModelSettings, 1)` を返す。`get_or_init_digest_settings()` も同様。

つまり:

- **モデル設定と API キー**(`model_settings`)は全ユーザー共通。1人が変更すると全員に波及する
- **ダイジェスト設定と SMTP パスワード**(`digest_settings`)も全体で1つ。配信先も送信者も共通

### 2.3 使用量はどこにも保存していない

Anthropic API のレスポンスに含まれる `input_tokens` / `output_tokens` /
`cache_read_input_tokens` は、`services/anthropic_client.py` などで
`logger.info(...)` に出しているだけで、DB には記録していない。

したがって「誰がどれだけ使ったか」を答えられる状態にない。課金・クォータ・使用量画面は
いずれもこの記録がないと成立しない。

### 2.4 発行済みトークンを失効させる手段がない

`services/auth.py` の `create_token()` はペイロードが `{"uid": user.id}` のみ。
有効期限(TTL)以外に失効の仕組みがなく、「全デバイスからサインアウト」や
「パスワード変更時に既存セッションを切る」ができない。

なお、このトークンは暗号化保存(`SECRET_ENCRYPTION_KEY`)と**同じ Fernet 鍵**を使うため、
鍵のローテーションで一括失効させる運用は取れない(保存済みシークレットが巻き添えになる)。

## 3. 設定機能の全体像

Claude アプリの分類(一般 / アカウント / プライバシー / 請求 / 使用量)に対応させつつ、
このアプリ固有の事情を加えたもの。**太字は現在存在しない機能**。

### 3.1 General(ユーザーごと)

- テーマ(実装済み。アカウントメニュー内)
- **既定のモデル**: 現在は `model_settings` のグローバル値。個人の好みとして持たせる
- **既定のソース件数**
- **レポートの既定のトーン・長さ**

### 3.2 Account(ユーザーごと)

- メールアドレス表示 / パスワード変更(実装済み)
- **表示名**: `users` テーブルはメールしか持たず、監査ログの表示もメールのみ
- **全デバイスからサインアウト**: 2.4 のとおりトークンにバージョン番号などの失効手段が要る
- **アカウント削除 / 自分のデータのエクスポート**(GDPR 等への対応)

### 3.3 Workspace / Organization(管理者)

Claude の個人向け設定にはない階層だが、このアプリは組織で使う前提なので必要。

- メンバーと権限(実装済み `/users`)
- 共有ペルソナ(実装済み `/personas`)
- 監査ログ(実装済み `/activity-log`)
- **ライブラリを個人用にするか組織共有にするかの選択**

### 3.4 Privacy & Data

- **保存期間の設定**: リサーチ履歴・アップロード文書を何日で自動削除するか
- **データのエクスポート / 削除**
- **外部送信先の開示**: 入力内容は Anthropic と Tavily に送信される。公開サービスとして
  提供するなら副処理者(subprocessor)として明示が必要
- 入力内容を学習に使わない旨の明記(Anthropic API の既定動作の説明を含む)

### 3.5 Billing & Usage(最も未整備)

- **使用量の計測**: 実行回数・トークン数・Tavily 検索回数をユーザー/組織ごとに記録
- **クォータとレート制限**: 未実装。1回のリサーチで Opus 5 を複数回呼ぶ
  (クエリ分解 → 要約 → 統合 → ギャップ再調査)ため、無制限公開はコスト面で危険
- **プランと上限到達時の挙動**(停止するか、低コストモデルに落とすか)
- **API キーの方針**(要判断): 顧客持ち込み(BYO)か、こちらのキーで動かして課金するか

### 3.6 Notifications

- **ダイジェストの配信先・スケジュールをユーザーごとに**(現在は全体で1つ)

## 4. 実装フェーズ

### フェーズ1 — データのスコープ化(前提条件)

**やること**

- `users` の上に「組織(organization/workspace)」を置くかを決める(→ 6.1 の判断事項)
- 上記テーブルに `owner_id`(および必要なら `organization_id`)を追加
- 既存の全クエリに絞り込みを追加。特に RAG 検索(`services/rag_service.py`、
  ChromaDB・BM25 インデックス)は**インデックス側にもスコープのメタデータが必要**で、
  ここが最も見落としやすい
- `model_settings` / `digest_settings` を単一行から所有者ごとの行へ
- 既存データの移行(現在の全レコードを最初の管理者に割り当てる等)

**リスク**: 影響範囲が最も広い。絞り込みを1か所でも入れ忘れると情報漏洩に直結するため、
「所有者でフィルタしていないクエリが残っていないか」を検証するテストを先に用意する。

### フェーズ2 — 使用量の計測とレート制限

**やること**

- `usage_events` テーブルを新設(ユーザー、機能、モデル、トークン数、発生時刻)
- `anthropic_client.py` の各呼び出しで、現在ログ出力しているだけの `usage` を記録
- Tavily の検索回数も同様に記録
- ユーザー/組織単位の上限と、超過時の挙動を実装

**単体でも価値がある**: 公開前でも、コスト事故(想定外の課金)を防ぐ意味がある。

### フェーズ3 — Account / Privacy

- 表示名の追加
- トークン失効の仕組み(`users` にトークンバージョンを持たせ、`verify_token` で照合)
- データのエクスポート / アカウント削除
- 保存期間の設定と、期限切れデータの削除処理

### フェーズ4 — 課金

フェーズ2の計測データが実際に貯まり、1顧客あたりの原価が見えてから着手する。
先に作ると、想定と実測がずれて作り直しになる。

## 5. 設定画面の構成案

現在の `/settings` は単一ページ(モデル設定・API キー・パスワード変更)。
上記を収めるならタブ分割が必要。

```
Settings
├─ General        テーマ / 既定モデル / 既定ソース件数 / レポート既定値
├─ Account        表示名 / メール / パスワード / セッション / エクスポート / 削除
├─ Notifications  ダイジェストの配信先とスケジュール
├─ Privacy        保存期間 / 外部送信先の開示 / データの取り扱い
├─ Usage          使用量の推移と当月の消費(フェーズ2以降)
├─ Billing        プランと支払い(フェーズ4以降)
└─ Workspace      メンバー / ペルソナ / 監査ログ / API キー  ※管理者のみ
```

管理者向け項目(現在アカウントメニューに入れている Activity Log / Personas / Users)は、
この Workspace タブに集約する案もある。ただしアカウントメニューからの導線は残す方が
到達しやすい。

## 6. 未決事項(判断が必要)

### 6.1 テナントの単位

- **案A: ユーザー単位** — 個人向けツールとして公開。実装は軽い
- **案B: 組織単位** — 組織の中で共有し、組織をまたいでは見えない。政策調査は
  チーム作業になりやすく、共有ペルソナや共有ライブラリという既存の作りとも整合する

Bを選ぶ場合、`organizations` テーブルと、ユーザーの所属関係が追加で必要になる。

### 6.2 API キーの持ち方

- **案A: 顧客持ち込み(BYO)** — こちらは API 費用を負担しない。課金設計が単純になる。
  ただし顧客に Anthropic と Tavily のアカウント取得を求めることになる
- **案B: こちらのキーで動かし、使用量に応じて課金** — 顧客の導入は容易。ただし
  与信・上限管理・不正利用対策が必須になる

### 6.3 既存データの扱い

現在のローカル/本番データを、移行時にどのユーザー・組織へ割り当てるか。
