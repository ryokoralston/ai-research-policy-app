### T-01 PDF エクスポートが本番で 500 になる
- 重要度: **High** / 検証: **[実測]** / 担当: **Sonnet**
- 場所: `backend/utils/pdf_renderer.py:9`（`_JP_FONT = "/System/Library/Fonts/ヒラギノ角ゴシック W3.ttc"`）、`:29`（`font = "Helvetica"` フォールバック）
- 現象: macOS 専用フォントが無い環境（Render = Linux）では fpdf2 のコアフォント Helvetica に落ちる。fpdf2 のコアフォントは latin-1 しか書けず、`—`（U+2014）ですら `FPDFUnicodeEncodingException` を投げる。venv で実測:
  ```
  'a → b'  RAISES FPDFUnicodeEncodingException
  'x ≥ 3'  RAISES
  'em — dash' RAISES      ← Claude の出力にはほぼ必ず含まれる
  '日本語'  RAISES
  ```
  つまり `GET /api/reports/{id}/export?format=pdf` と `GET /api/analysis/{id}/export?format=pdf` は本番でほぼ常に 500。
- 変更:
  1. `backend/assets/fonts/DejaVuSans.ttf` と `DejaVuSans-Bold.ttf` をリポジトリに追加（DejaVu は自由ライセンス、合計 約 1.4 MB。ライセンスファイル `LICENSE-DejaVu.txt` も同梱）

  3. `pdf.add_font("DejaVu", "", path)` / `add_font("DejaVu", "B", bold_path)`
- 触らない: `render_markdown` / `_write_inline` のロジック、`utils/export.py`
- 検証:
  ```bash
  cd backend && ./venv/bin/python -c "
  from utils.export import render_pdf
  b = render_pdf('Title — with dash', 'x ≥ 3 → ok\n\n- 日本語 bullet')
  assert b[:4] == b'%PDF', b[:20]; print('ok', len(b))"
  ```
  これに加えて `tests/test_export.py` と全ランナー。**フォントを一時的に隠して**（`_JP_FONT` をダミーパスにして）同じコマンドが通ることを確認する — Hiragino のある Mac で通っただけでは本番の再現になっていない。

### T-08 ログイン制限が X-Forwarded-For の先頭で鍵付けされている — **完了（2026-09-18）**
- 重要度: **High（本番で成立すれば）** / 検証: **[実測・本番確認済み]** / 担当: **Opus** / **前提: §6 (a) の結果**
- 場所: `backend/services/auth.py:37-43` `client_ip()`（`forwarded.split(",")[0]`）、`:34` `_login_failures`
- 現象: リバースプロキシは通常 XFF を**末尾に追記**するので、先頭はクライアントが自由に書ける。攻撃者はリクエストごとに XFF を変えるだけで 5 回/5 分の制限を無限に迂回できる。監査ログの `ip_address` も汚染される。
- **§6(a) 実測結果（2026-09-18、本番に対してユーザーが実行）**: `X-Forwarded-For: 203.0.113.9`（単一値）を付けて叩く → Activity Log にその偽装値がそのまま記録。同じリクエストから XFF を完全に外す → 実際の外部 IP が記録。**結論: Render は XFF を一切検証・上書きしない（素通し）。** これにより下書きの案 A・案 B は両方とも不採用と判明：
  - 案 A（最後のホップを使う）は、単一値の偽装（カンマ無し）には無力 — 今回の実測がまさにその形で成立していた
  - 案 B（`uvicorn --forwarded-allow-ips='*'`）は `request.client.host` を同じ偽装可能な XFF で上書きさせるだけで、脆弱性を ASGI 層に移すだけ
- **1回目の修正（不十分・却下）**: `client_ip()` から XFF 読み取りを削除し `request.client.host` のみを返す形にした（コミット `7e40ba0`）。デプロイ後に本番で同じ偽装テストを再実行したところ**まだ突破可能**と判明（`203.0.113.9` がそのまま記録された）。デプロイ反映のタイミング競合ではないことを Render ダッシュボードの Deploy Live 時刻と突き合わせて確認済み。原因: このデプロイ環境では `request.client.host` 自体が、Render 内部の層で（推測だが）攻撃者が送った XFF の影響を受けて決まっているらしく、生のソケット接続元を素直に反映していない。
- **2回目の修正（本番で実際に確認・採用）**: 調査の過程で `server: cloudflare` / `cf-ray` レスポンスヘッダーから **Render は onrender.com 全体を自動的に Cloudflare 経由でホストしている**ことが判明（Render 自身のプラットフォーム機能、本プロジェクトの設定ではない）。`CF-Connecting-IP` を自分で偽装しようとすると **Cloudflare のエッジが 403 で弾き、Render・アプリには一切届かない**ことを実測（`x-render-origin-server` ヘッダーが応答に無い＝アプリまで到達していない証拠）。一方 `True-Client-IP` は偽装してもブロックされず素通りしたため保護状態が確認できず不採用。`X-Forwarded-For` は正規のリクエストでは先頭が本物の IP になる（Cloudflare は末尾に自分のホップを追記するだけで先頭を書き換えない）が、クライアントが先頭に偽値を差し込めるため信頼できないと結論。**採用: `CF-Connecting-IP` ヘッダーが存在すればそれを信頼し、無ければ `request.client.host` にフォールバック**（コミット `ead9183`）。`_login_failures` の `_MAX_TRACKED_IPS = 10_000` 上限（FIFO 追い出し）は 1 回目の修正のまま維持。`tests/test_auth.py` に回帰テスト追加、修正前のコードに対して実際に失敗することを確認した上での実装。全 59 ランナー緑。**本番で 2 段階の実測により最終確認済み**（XFF 偽装 → 実 IP が記録される／`CF-Connecting-IP` 偽装 → 403 でアプリに届かない）。
- **教訓**: `request.client.host` が「生のソケット接続元だから安全」という前提は、マネージドホスティング環境では自明ではない。本番での実測（デプロイ後の再テスト）なしに「コードを直したから安全」と判断するのは危険 — 1 回目の修正はローカル推論としては筋が通っていたが、本番の実際の挙動とは違った。
- 触らない: `check_login_rate_limit` のウィンドウ値（変更なし、確認済み）
